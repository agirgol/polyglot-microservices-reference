# ADR 0010: Handler code is generated before the process starts

**Status:** Accepted
**Date:** 2026-08-21

## Context

Wolverine does not invoke handlers by reflection. It generates a class per
handler that resolves dependencies and calls the method directly, which is where
its speed comes from. The question is only when that code is produced.

By default it is produced at runtime, by Roslyn, on first use — which is why
`WolverineFx.RuntimeCompilation` had to be added at all (ADR 0001 notes Wolverine
6 removed the compiler from the core package). A trace taken shortly after a
restart showed the first request through this service costing 731 ms, and the
suspicion was that most of it was that compilation.

## Decision

Generate the code ahead of time and commit it:

```sh
dotnet run --project services/orders/src/Orders -- codegen write
```

`TypeLoadMode.Static` outside Development, so the running process loads those
types and never invokes a compiler. `TypeLoadMode.Auto` in Development, because
generated code that has to be regenerated by hand after every handler change is
generated code that will be stale.

## Consequences

**Measured, on one machine against the same database:**

| | first request | second |
|---|---|---|
| Runtime compilation | 1.098 s | 0.012 s |
| Pre-generated, `Static` | 0.430 s | 0.012 s |

About 670 ms off the first request. Nothing changes for the second.

**The 430 ms that remains is not Roslyn.** It is EF Core building its model, the
Npgsql pool opening its first connection, and the request pipeline being jitted.
The original suspicion was right about the largest part and wrong about the
whole: a trace showing 731 ms invites the conclusion that it is all one thing.

**Generated code is committed and can go stale.** A handler signature that
changes without a re-run leaves a service that starts and behaves as it did
before the change — the exact failure `TypeLoadMode.Auto` in Development exists
to prevent locally, and one that nothing currently catches in CI.

**Roslyn is still in the image.** `WolverineFx.RuntimeCompilation` remains
referenced, because `codegen write` needs it and Development uses it. The win
here is startup time, not image size.

## The part that pointed nowhere near itself

Making the command available means calling `RunJasperFxCommands`, and doing that
broke every integration test with:

```
System.InvalidOperationException : The server has not been started or no web
application was configured.
```

Guarding it behind `args.Length > 0` did not help, which was the confusing part
— in a test there are no arguments, so the call never runs. JasperFx installs
itself when the assembly is used at all, and `WebApplicationFactory` was left
with a host whose services resolved and whose web server had never started.

The fix is one line in the test fixture, `JasperFxEnvironment.AutoStartHost =
true`, and finding it took bisecting the change rather than reading the error,
because the error names a test-host concept and nothing above it mentions
JasperFx.

`TheHostStartsTests` now asserts the two halves separately — services resolve,
and the application serves HTTP. If only the second fails again, the next person
starts from the right end.

## Alternatives considered

**Leave it dynamic.** 670 ms once per process start is not much for a service
that runs for weeks. It is a great deal for a rolling deploy where every new pod
pays it behind a readiness probe, and it is most of what a reader sees on the
first trace they take.

**Generate during the container build instead of committing.** Keeps the
repository free of generated code and makes staleness impossible. It also means
the build needs the full configuration — a connection string, a broker address —
because `codegen write` builds the host to discover handlers. Trading a
committed artefact for a build that cannot run without infrastructure is the
worse deal here.

**Native AOT.** Removes the JIT cost too, and Wolverine documents
`TypeLoadMode.Static` as a prerequisite for it — this decision is the first step
either way. Not taken further: EF Core and Npgsql under AOT is its own project.
